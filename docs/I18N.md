# Arabic + RTL — how to add it to a new thing

The architecture and the reasoning behind it are in
[ADR-0007](decisions/ADR-0007-arabic-locale-routing-and-content-storage.md),
amended by
[ADR-0008](decisions/ADR-0008-machine-generated-arabic-first-draft.md) — which
is the one to read before assuming a curated surface has to be hand-authored.
This file is the practical half: what you have to do when you add a new X.

**A new field starts with a machine first draft, not with a blank.** Add it and
the generator picks it up: `npm run i18n:content -- --page <key> --dry-run` to
see it, without the flag to write it. Whatever the gates reject stays English
and lands on a review list, which is the designed outcome rather than a
failure.

**The one rule:** the Arabic value sits immediately beside its English sibling,
at whatever depth the sibling lives. A column beside a column; a `<key>_ar` key
beside a `<key>` key inside any jsonb bag, including inside a list item.

> **Status: P0–P3 complete, Arabic built but not switched on.** The route tree
> lives under `app/[locale]/`, the whole codebase uses logical direction
> utilities, next-intl and the Arabic font are wired, and the language switch
> is in the navbar — but `LOCALES` in `lib/i18n/locales.ts` is still `["en"]`,
> so none of it is served or indexed yet. Adding `"ar"` there is the launch.
>
> It has been exercised: a local build with both locales prerendered 234
> `/ar/*` routes alongside 234 `/en/*`, mirrored the chrome, and loaded the
> Arabic face on `/ar/*` only. Sections marked _(from P4)_ land later.

---

## The two locale lists

`lib/i18n/locales.ts` holds both, and the distinction matters:

| | Meaning | Used by |
|---|---|---|
| `ALL_LOCALES` | every locale the code knows how to render | the `Locale` type, so `locale === "ar"` branches typecheck |
| `LOCALES` | the locales actually served right now | routing, sitemap, `generateStaticParams`, the navbar toggle |

Arabic is in the first and not (yet) the second. That is what lets Arabic-aware
code be written and reviewed before anything serves it — and it is the kill
switch, because once `/ar` is indexed, turning it off is a 410-and-Search-Console
exercise rather than a flag flip.

## I added a new page / route

1. It goes under `app/[locale]/` like everything else. Nothing to do for the
   URL — `/foo` and `/ar/foo` both fall out of the segment.
2. **A page's `generateStaticParams` needs no locale.** Next runs a child
   `generateStaticParams` once per set of params the parent produced and merges
   them, so returning `{ slug }` yields `{ locale, slug }` for free.
3. **A metadata file's `generateStaticParams` does.** `opengraph-image.tsx`,
   `icon.tsx` and friends do *not* compose that way — wrap the return in
   `withLocales()` from `lib/i18n/static-params.ts`. This is not theoretical:
   the P1 move silently dropped all ~51 prerendered OG images while the routes
   still reported as SSG. Nothing errored; the cards would just have been
   generated on first request forever.
4. Add `alternates` from `lib/i18n/metadata` so it emits `hreflang` _(from P3)_.
5. **Route handlers** (`route.ts`) are different: if the URL is referenced
   externally — a registered OAuth redirect, a printed QR code, a shared
   permalink — it stays at the app root and goes in `NON_LOCALISED`
   (`lib/i18n/non-localised.ts`). `lib/i18n/non-localised.test.ts` walks the app
   tree and fails if a handler is not covered, so you will be told. Note this
   is about *URL shape*, not language: `staff-invite` is English-only content
   but lives under `[locale]`, because a page outside the segment would have no
   root layout to render into.
6. Once next-intl lands _(P3)_, add `setRequestLocale(locale)` to the page and
   every layout above it. Forget it and the route silently drops to dynamic
   rendering — it still renders correctly, it just loses CDN caching and
   discards its `revalidate`. `scripts/ci/assert-static-routes.mjs` catches
   this, comparing against `scripts/ci/route-render-baseline.json`.

## I added a link

Import `Link` from `@/components/i18n/link`, not from `next/link`.

Hrefs in this repo are written absolute and English — `/insights`,
`/p/${slug}` — which was correct while one locale was served and became a bug
the day `LOCALES` grew. The locale is *in the URL*, so an href that omits it is
an href back to English. On `/ar/buy` that was 46 of 56 internal links: a
visitor who switched language was switched back by their next click.

The wrapper adds the prefix from `usePathname()`, and for English it is the
identity function, so nothing about an English page changes.
`lib/i18n/no-bare-link.test.ts` fails the build if a public file imports
`next/link` directly. `/admin` is exempt and stays on `next/link` — the CMS is
English-only and the proxy redirects `/ar/admin` back out.

A plain `<a href="/…">` is not covered — no lint rule can tell one from a
`mailto:`, a `tel:` or a `#anchor` reliably enough to gate a build. Neither is
`router.push`, a `redirect()` out of a Server Action, a form `action`, or a
link someone was sent. Those are caught at runtime instead: `proxy.ts`
redirects an unprefixed URL to whatever locale the visitor chose, so the worst
case is one redirect hop rather than a silent drop into English.

**The choice is a cookie, and only an explicit one counts.** The language
switch links carry `?setlang=<locale>`; the proxy writes `l=` into `bz_prefs`,
strips the param and redirects to the clean URL. No `l=` means no redirect at
all, which is what keeps crawlers — and therefore the index — on exactly the
URLs they see today. It is also why the English half of the switch needs the
param: without it a sticky Arabic session has no exit, and clearing cookies is
the only way out.

## I added a new component with visible text

Do not write the English inline. Put it in `messages/en/<namespace>.json` and
read it with next-intl _(from P3)_. `lib/i18n/messages.test.ts` asserts every
key exists in both locales, and that no Arabic value is byte-identical to its
English one — which is what catches "someone pasted the English into `ar.json`
to make the test pass".

Anything with a plural needs ICU plural syntax with **all six** Arabic
categories (`zero`, `one`, `two`, `few`, `many`, `other`). This is the single
reason the project uses next-intl rather than a hand-rolled `t()`.

## I added a new section, library section or Page Builder block

**Nothing to do.** This is the point of the derived-twin design _(from P4)_:
the Arabic input is generated from your `FieldDef`, so every `text` and
`textarea` field gets an Arabic twin automatically, in the editor and in
storage. That covers all five registries — master pages, sub-pages, the section
library (`lib/master-pages/library.ts`), the search-results headers
(`lib/master-pages/search-headers.ts`) and the Page Builder catalogue — because
all five hand the same `FieldDef[]` to the same editor and the same validator.

Two things you *might* need:

- **Opt a field out** with `i18n: false` when it holds *data wearing a text
  field* — an area slug, a lucide icon name, a social network name, a
  lead-routing tag, a render token, a phone number, `09:00`. The default is on,
  deliberately: a forgotten opt-out costs one unused input, while a forgotten
  opt-in costs a permanent hole nobody finds until a customer does.

  The ones that matter are the ones **an Arabic proofreader cannot find**.
  Fold `slug` into Arabic and the area resolves to nothing and the card
  vanishes — the Arabic on the page reads perfectly, and it surfaces weeks
  later as *"the communities grid is empty on the Arabic site"*.

  **Judge the field by the values it actually holds, not by its name.** This
  doc used to give a stat value (`"2,400"`) as the headline example, and that
  was wrong in the most expensive direction: `statList()` is shared by twelve
  sections and holds `"78%"` on `/off-plan` but `"Homes + offices"` and
  `"Whole-cost"` on `/rent` and `/commercial`. Opting it out would have
  stranded eight visible strings in English on the busiest landing pages. A
  field whose values are *mixed* stays translatable — the numeric ones are
  protected by masking at translation time, which can tell them apart.
  Conversely `sell/pricing.range_low` sounds numeric and holds `"Low"`.

  `lib/i18n/non-prose.test.ts` (G-16) runs the check for you over every
  shipped default; `lib/i18n/prose.ts` is the heuristic.
- **Hand-declare a twin** only if it needs its own label or an Arabic default.
  `lib/master-pages/sections/contact-qr.ts` does this for its 14 fields. A
  hand-declared twin wins over the derived one; `lib/master-pages/i18n.test.ts`
  asserts no *other* module declares one, because two twins for one field would
  render the input twice.

Never name a field key ending in `_ar` yourself outside that file.

## I added a new column with public text

1. Add the twin column in the same migration: `description` → `description_ar`.
2. **Check whether the table has column-level grants.** `site_settings` is the
   only one that does (migrations 0096/0097), and there an ungranted column
   fails the *whole* PostgREST select — so a missing grant means every public
   page silently loses its branding and falls back to code defaults. Every other
   table uses table-wide grants plus RLS and needs nothing.
3. Register the column in `lib/i18n/domains.ts` with a strategy — `hand`,
   `machine` or `never` — and a `file:line` showing where a visitor reads it.
   A brand-new table must be added there too, even one with no text at all:
   `domains.test.ts` enumerates every table in `db/types.ts` and fails on any
   it cannot find, so an unclassified table is a red build rather than a
   silent hole. A developer adding a `FieldDef` gets Arabic free; a developer
   adding a *table* gets nothing without this.

   Every registered column already has its twin (migration 0104), so
   `AWAITING_TWIN` is empty and should stay that way — a new column adds its
   `_ar` sibling in the same migration.

4. Add the column to `WIRED_EDITOR` once a CMS form can type into it, and to
   `WIRED_READ` once its public query folds the locale. Those two lists are the
   honest half: a twin column existing is not the same as a person being able
   to reach it, nor as the page rendering it, and conflating the three is how
   `developers` shipped columns nobody could edit. `domains.test.ts` prints
   whatever is still missing from each.
5. Re-run `npm run db:types`.

## I added a new form field

Forms are the one surface the choke point does **not** reach _(from P7)_.
`mergeCopy` in `lib/forms/resolve.ts` iterates the registry literal, which has
no `_ar` keys, so Arabic there is explicit: `FormCopy` carries `*_ar` keys and
`form_fields` carries `label_ar`/`placeholder_ar`/`help_ar`/`unit_ar`.

Two traps in that file:

- `_actions.ts` enumerates every copy key explicitly on write. Miss one and
  every save destroys that field's Arabic.
- Three service forms take their heading and CTA copy from master-page section
  values and render it read-only (`FormDef.copyFromPage`). Reproduce that for
  Arabic too — a second writable copy would drift silently in a language most
  editors cannot proofread.

## I'm extracting a component that has counts in it

Split it. **A string with a number in it stays in the message catalogue; the
prose around it can move to the CMS.**

Arabic agrees a sentence with its count across six plural categories, and a CMS
text input has no way to express that — an editor typing `{count} عقارات` is
wrong for one, two and eleven, and nobody who reviews the save can see it. So
`"8 of 25 · saved to this browser"` became `savedCount` in the catalogue
(`"{count} of {max} · {note}"`) with `{note}` interpolated from the CMS
document. The editor still owns the words; ICU still owns the agreement.

The `shortlist` and `compare` library sections
(`lib/master-pages/library.ts`) are the worked example, and their `dataNote`
tells the editor which lines are missing from the form and why.

**A client component cannot read its own document.** `ShortlistDrawer` renders
in the public layout, so its copy is resolved there with
`getShortlistCopy(locale)` and threaded down as a prop. Adding a fifth read to
that layout is safe as long as it uses the cookie-free public client — a
`cookies()` read there drops every public route out of ISR.

**Defaults need an entry in the Arabic store.** A section's English defaults
resolve their Arabic through `arabicFor` (`lib/master-pages/arabic.ts`), so a
new default with nothing in `lib/master-pages/arabic/master.json` renders
English on `/ar` even though the twin machinery is working perfectly. Either
run `npm run i18n:content`, or hand-author the entry with `by: "human"` —
`store-catalogue-agree.test.ts` (G-18) will tell you if it disagrees with a
catalogue string holding the same English.

The third option, and the right one when the Arabic already exists somewhere
curated: declare the twin in `defaults` beside its English sibling, the way
`lib/master-pages/sections/mortgage.ts` and
`lib/master-pages/search-headers.ts` do. `mergeValues` never overwrites a twin
that already has a value, so a hand-declared default outranks the store without
having to touch a 700 KB generated file. Declare it in `defaults` only — a
`*_ar` entry in `fields` is what `lib/master-pages/i18n.test.ts` forbids
outside `contact-qr.ts`, because a declared twin and a derived one render the
input twice.

## I need to invalidate a cache after a write

Use `revalidateLocalised()` from `@/lib/i18n/revalidate` for any **public**
path. Keep raw `revalidatePath()` for `/admin/*` and for root metadata routes
(`/sitemap.xml`, `/robots.txt`, `/opengraph-image`), which live outside the
locale segment.

`lib/i18n/revalidate.test.ts` fails the build otherwise, and it is worth knowing
why it is that strict: under `[locale]`, a bare `revalidatePath("/buy")` names a
cache key that no longer exists. It does not throw. The CMS shows "Saved.", the
public page keeps serving stale content, and it reads as a caching bug for a
week.

## I'm adding a route handler that reads content

Take the locale as a parameter. Do not call `currentLocale()`.

`/api/*` is in `NON_LOCALISED`, so a route handler never sits under `[locale]`,
nothing calls `setRequestLocale` for it, and next-intl's `requestLocale` is
undefined — `currentLocale()` answers `en` for every caller, including one on
an Arabic page. It does not throw and it does not warn. `/api/shortlist` spent
its whole life like this: the shortlist card listed English titles while the
compare page one click away, reading the same query, listed the Arabic.

So the caller says which locale it wants (`?locale=ar`, validated with
`isEnabledLocale`) and the query takes an override that beats the ambient read.
Pin the override with a spec — one that fails if it merely *exists* but loses
to `currentLocale()` — the way `lib/queries/compare.fold.test.ts` does.

## I'm writing CSS

Use logical utilities, always: `ms-`/`me-` not `ml-`/`mr-`, `ps-`/`pe-` not
`pl-`/`pr-`, `start-`/`end-` not `left-`/`right-`, `text-start`/`text-end`,
`border-s`/`border-e`, `rounded-s`/`rounded-e` _(from P2)_.
`lib/rtl/no-physical-utilities.test.ts` enforces this repo-wide.

Three cases where a physical value is **correct** and must not be converted:

- Centering pairs — `left-1/2` with `-translate-x-1/2`. `start-1/2` flips while
  the translate does not, and the element jumps half its width.
- Anything inside a `data-[side=left|right]:` chain. Radix's `data-side` is
  physical placement, so a physical animation matching it is already right.
- A map pin positioned from `map.project()`. Geography is not a reading
  direction — never mirror a map, only its chrome.

For Arabic typography, target `:lang(ar)` rather than `[dir="rtl"]`, so a Latin
quotation inside an Arabic page keeps the brand face.

## I'm writing text that mixes Arabic and Latin

Use the helpers in `lib/i18n/bidi`. The cases that break without
isolation: phone numbers (`+971…` — the `+` is a neutral and jumps to the wrong
end), reference codes (`BR-1042` renders as `1042-BR`), prices, and areas.

`isolateLtr` for values you know are Latin (prices, references, permits, phone
numbers). `isolateAuto` for anything user- or DB-supplied, which may arrive in
either script — an area name folds to Arabic on `/ar` and stays Latin when the
twin is blank, and the caller cannot know which it got. `isolateForLocale` when
you need English to stay byte-identical, which is every PR while `LOCALES` is
`["en"]`.

In the DOM, prefer CSS: `globals.css` already isolates `.mono`, so a price or
reference inside a `.mono` span needs nothing from that module.

In plain-text contexts — `title`, `og:title`, PDF strings, feed XML, WhatsApp
templates — there is no element to hang a `dir` on, so use the isolate
characters `LRI`/`FSI`/`PDI`. Never `RLE`/`LRE`/`RLO`/`LRO`: those leak across
element boundaries, and `bidi.test.tsx` sweeps the catalogues for them.

English shown inside an Arabic page goes in `<EnglishFallback>` from
`lib/i18n/english-fallback` — that is the `<span lang="en" dir="ltr">` ADR-0007
§5 commits to, and the thing `:lang(ar)` typography was written against.

**Testing a component that reads messages.** Use `renderWithIntl` from
`lib/i18n/test-utils`, not bare `render()`. Without a provider `use-intl`
*throws* — "No intl context found" — rather than failing an assertion, so the
stack trace says nothing about the change that caused it. The harness loads the
real catalogue, so a renamed key fails the test that renders it.

## I'm touching an OG image or a PDF

Both stay English in both locales, and both are blocked on the same thing —
text layout, not translation.

**OG images.** Satori shapes Arabic correctly but never reorders it, so words
lay out left-to-right and the sentence reads backwards; `direction: "rtl"` on a
text node is ignored outright (`flexDirection: "row-reverse"` does work, so the
card *chrome* could mirror). A bidi pre-pass renders a single line correctly,
including Latin islands like `AED 2,500,000`, and then breaks on the first wrap
— which is fatal for cards whose job is to hold titles. Fixing it means
choosing the line breaks ourselves with font metrics Satori does not expose.
`lib/og/arabic-og.test.ts` fails if an OG route starts reading Arabic content;
it holds the full measurements.

**PDFs.** `@react-pdf/renderer` has real bidi and shaping but calls Yoga's
`calculateLayout` with no direction argument and exposes no logical style
props, so every `flexDirection: "row"` lays out LTR regardless. Downloads on an
Arabic page are labelled via `pdfLabel()` in `lib/pdf/language-note.ts`.

In both cases an English artefact is an unfinished feature and a backwards
Arabic one is a broken feature. Don't ship the half-measure.

## I'm adding something that machine-translates

Add the field to `lib/i18n/mt/targets.ts`, and add its `_ar` twin column in the
same migration — `targets.test.ts` fails if a registered target has nowhere to
store its result, and reads the real column names out of `db/types.ts` so an
invented one cannot ship.

Before you add it, check it is not in `PROTECTED_FIELDS`: permit numbers,
BRN/ORN, prices, visitor-authored reviews and internal advisor notes are never
machine-translated. Legal and consent copy is protected too but is not in that
list, because none of it is a database column — it is JSX and message-catalogue
strings, so nothing an MT target can name.

Protected spans inside translatable prose are masked to sentinels (`⟦0⟧`)
before the model sees anything, which is why a price cannot be corrupted: the
model never receives it. Mask proper nouns as well and pass their hand-authored
Arabic through `unmask`'s `overrides` — that is how an area gets its canonical
toponym instead of a fresh transliteration on every record. Anything left
unmasked and untranslated surfaces as a `latin-leak` finding.

`validate()` runs on the masked output before any write, and a failure does not
write: sentinel integrity, numeral drift (script-blind, so Arabic-Indic digits
are not drift), Latin leak, length, and glossary violations. An all-English
field is the designed fallback; a wrong Arabic field is live until someone who
reads Arabic happens to look.

**There is no job queue, no row trigger and no sweep cron.** The published
corpus is 18 properties — 54 strings — so translation is driven from the CMS.
The plan carried a durable queue for a corpus two orders of magnitude larger
than the real one. If it grows, the queue goes in then and none of the above
changes.
